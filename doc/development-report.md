## 1. 出発点

作業前のモデルは、次の状態でした。

- 学習データは `train_model.py` の中で自動生成した**サンプル600件**
- ラベルは天気から if 文で一意に決まるルール
- そのルールをランダムフォレストに学習させ、正解率はほぼ 100%

つまり**自分で書いたルールを丸暗記させて満点を取っていた**だけで、機械学習として意味のある部分がありませんでした。ここを作り直すことが今回の出発点です。

## 2. データセットを実測に置き換える

Open-Meteo の過去データAPI（ECMWF ERA5 再解析、CC BY 4.0・APIキー不要）から、日本9都市の実測気象データを取得しました。

| ファイル | 用途 | 行数 | 期間 |
| --- | --- | --- | --- |
| `data/weather_jp.csv` | 学習・検証 | 19,728 | 2019-01-01 〜 2024-12-31 |
| `data/weather_jp_holdout.csv` | 未来データ（学習後に一度だけ使う） | 5,373 | 2025-01-01 〜 2026-08-20 |

対象都市は札幌・仙台・新潟・東京・名古屋・大阪・高知・福岡・那覇の9都市です。1時間ごとの実測から、お出かけ時間帯（9〜18時）だけを取り出して1日1行に集計しています。

降水確率は過去データに存在しない値（予報にしかない）ため、「その10時間のうち雨が降っていた時間の割合」で代用しました。0〜100の11段階になること、雪も降水に含まれることは、限界として明記してあります。

未来データを分けたのは、**学習が終わったあとに一度だけ見る、まったく触っていないデータ**を残すためです。何度も見て調整したデータで測った成績は、良く出て当たり前になります。

詳細は [dataset.md](dataset.md)。

## 3. モデルを4つ作る

機械学習の3つの型（分類・回帰・教師なし）がひと通り入る構成にしました。

| # | モデル | 種類 | 成績 | 説明 |
| --- | --- | --- | --- | --- |
| ① | カテゴリ予測 | 分類 | 正解率 **0.817**（上限 0.822 ／ 未来データ 0.821） | [README.md](README.md) |
| ② | 翌日の天気予測 | 時系列の回帰 | 気温 MAE **1.65℃**（持続予報比 7.7%改善） | [forecast.md](forecast.md) |
| ③ | おでかけ日和度 | 回帰 | MAE **4.72点**（下限 4.65点） | [comfort.md](comfort.md) |
| ④ | 天気タイプ分け | 教師なし | シルエット係数 0.266 ／ 安定性 ARI 0.991 | [weather-types.md](weather-types.md) |

### ラベルの作り方を変えた

①のラベルは実データに存在しないため、依然としてルールから作っています。ただし**確率にしてから抽選する**方式に変えました。

こうすると「屋外でも屋内でもよさそうな日」が混ざり、ルールの丸暗記では届かない上限が生まれます。これがベイズ限界 **0.826** で、この問題の満点にあたります。満点が定義できるので、成績を「上限に対してどこまで取れたか」で語れるようになりました。

最初の設計では indoor が 61% を占めて偏っていたため、おすすめ度の式を組み直し、indoor 38.8% ／ outdoor 33.1% ／ relax 28.1% に調整しています。

## 4. 評価を実務水準にする

点数を1つ出して終わりにせず、その数字が信用できるかまで確かめる作りに変えました。

| 観点 | やったこと | 分かったこと |
| --- | --- | --- |
| 信頼区間 | ブートストラップ法 | 正解率 0.817 [95%CI 0.805〜0.830] |
| 有意差 | マクネマー検定 | 2位のランダムフォレストとの差は **p=0.225、有意差なし** |
| 確率の質 | ECE と較正の検証 | ECE 0.0130。isotonic 較正は対数損失が悪化したため**不採用** |
| 内訳 | 都市別・季節別のスライス評価 | 新潟 0.787 〜 那覇 0.867 のばらつき |
| 時系列 | ウォークフォワード検証（年ごと） | 1回の分割では見えないばらつきを測定（気温 MAE の標準偏差 0.04） |
| 不確かさ | 分位点回帰による予測区間 | 想定80%に対し実測 **68.9〜89.0%** と較正不足 |
| 安定性 | 乱数を変えた調整ランド指数 | クラスタは安定（最低 0.991） |

### うまくいかなかった結果も残した

- ②は未来データで**風速だけ持続予報に負けた**（MAE 1.32 vs 1.30）
- ②の予測をカテゴリまで通すと、実測の天気で出したおすすめとの一致率は **61.8%**。予報の誤差はそのままおすすめのズレになる
- ③には点数帯ごとに**平均回帰**が出ている（低得点を +2.98、高得点を −1.85 に寄せる）
- ④のシルエット係数 0.266 は低い。天気には明確な切れ目がなく、タイプ分けは便利な見出しにすぎない

## 5. 基盤を整える

学習スクリプトに散らばっていた処理を `outing_ml/` パッケージに集約しました。学習時と推論時で値がズレる事故を、構造的に起こせなくするためです。

| モジュール | 役割 |
| --- | --- |
| `config` | しきい値・ハイパーパラメータ・パスの一元管理 |
| `data` | スキーマ検証（列・型・範囲・欠損・重複・日付連続性）と sha256 指紋 |
| `labeling` | おすすめ度モデルとおでかけ日和度の正解づくり |
| `features` | 時系列特徴量。未来情報の混入を検査する `assert_no_leakage` つき |
| `metrics` | 信頼区間・マクネマー検定・ECE・スライス評価・ピンボール損失 |
| `registry` | 成果物に特徴量順・データ指紋・gitコミットを同梱し、履歴を残す |
| `serve` | 入力検証つきの推論。学習範囲外の入力には警告を返す |
| `monitor` | PSI/KS によるドリフト監視 |
| `weather_source` | 気象データの取得と前処理（学習と本番で共通） |
| `forecasting` | 翌日予報と、そこから出すおすすめ |

ドリフト監視のしきい値は**KS検定のp値ではなく効果量**で判断するようにしました。件数が多いとごくわずかな差でも「有意」になり、いつも赤い監視は誰も見なくなるためです。この判断はテストで固定しています。

## 7. Web アプリと REST API

Gradio 版（`app.py` / :7860）に加えて、Flask 版（`webapp.py` / :5000）を作りました。画面5つと `/api` の8エンドポイントが同じサーバで動きます。

| URL | できること |
| --- | --- |
| `/` | 天気4項目の入力。都市を選んで「あしたの予報から」も選べる |
| `/predict` | 予測結果（確信度・おでかけ日和度・天気タイプ・確率の内訳） |
| `/forecast` | あしたの天気の予測（予測区間つき）と、そのおすすめ |
| `/plan` | 時間つきのお出かけプラン |
| `/models` | いま動いているモデルの版・成績・学習データの指紋 |

学習して置いてあるだけだった**②の翌日予測モデルを、実際に使える経路につなぎました**。都市名を渡すと、直近の実測を取得 → 翌日を予測（予測区間つき）→ そのままおすすめまで出します。

起動手順・API仕様・つまずいたときの対処は [webapp.md](webapp.md) にまとめました。記載したコマンド（`python webapp.py` / `flask --app` / `gunicorn`）は、すべて実際に実行して動作を確認しています。

## 8. 見つけて直した不具合

作りながら見つかったものです。多くは「実際に動かしたから分かった」類でした。

| 内容 | 見つけ方 |
| --- | --- |
| ラベルが indoor に 61% 偏っていた | 最初の学習結果を見て設計をやり直した |
| `maps_api.geocode` は APIキーが無いと **None ではなく例外を投げる**ため、`A() or B()` 形式の切り替えが働かず `/plan` が 500 | サーバを起動して実際に叩いた |
| CI が `pytest` で `outing_ml` を見つけられない（`python -m pytest` では通る） | main へマージしたあと CI が落ちた |
| CI の依存に flask が無い | マージ前に自分で気づいて先回りで修正 |
| まとめて予測で「何番目が悪いか」が分からない | テストが先に捉えた |
| 翌日予報の起点が7日古い日付になっていた | 出力を見て気づいた |
| コミットの著者が GitHub アカウントに紐づいていなかった | GitHub の画面を見せてもらって発覚 |

**CI の件は検証手順の穴でした。** 手元で `python -m pytest` を使っており、CI が使う `pytest` コマンドと `sys.path` の扱いが違うことを見落としていました。`pyproject.toml` に `pythonpath = ["."]` を設定し、以後は CI と同じコマンドで確かめています。

## 10. FreStyle — AIチャット履歴の PostgreSQL 移行

別リポジトリで1件、データストアの移行を行いました。

会話履歴だけが DynamoDB にあり、次の3つが構造的に解けない状態でした。

1. セッションを消しても履歴が別ストアに残る（DELETE が連動しない）
2. 並び順を DB に任せられない（取得後に Go 側で並べ直していた）
3. セッションと履歴を1トランザクションで書けない

`ai_chat_messages` 表を追加し、外部キー + `ON DELETE CASCADE`、`ON CONFLICT DO NOTHING`（SSE の再送で二重にならない）、並び順は SQL の `ORDER BY` に一本化しました。repository の interface は変えていないため、usecase と handler は無改修です。既存データを取り込む一度きりのコマンドも用意しました。

結合テスト4本・サブ8本を**本物の PostgreSQL 17.6** で通し、`make verify` の各段（gofumpt / vet / build / archlint / naminglint / sqlc-vet / apispec-lint）もすべて通過しています。

> **その後の状況**：この移行は現在**無効になっています**。別作業で AIチャット機能そのものが削除されたためです（`feat/frestyle-391-remove-ai-chat`）。関連する Go コードもマイグレーションのディレクトリも残っていません。作成したコミットはオブジェクトとしては残っていますが、指していたブランチは削除されています。

## 11. 残っている課題

- **ラベルは依然としてルールから作った疑似データ**です。これがこのモデルの最大の弱点で、直すには実際の利用データが要ります。第一歩として、REST API と画面が予測のたびに `reports/predictions.jsonl` へ入力と結果を残すようにしました（天気の数値と予測結果のみ。個人を特定できる情報は残しません）
- **降水確率は本物の予報値ではありません**。過去データに存在しないための代用です
- **②の予測区間が較正不足**です（想定80%に対し実測 68.9〜89.0%）
- **Hugging Face Space で動いているのは Gradio 版のまま**です。Flask 版を同居させるには Space の設定を `sdk: docker` に変える必要があります
- ②は本物の天気予報にはかないません。地上の4項目の過去3日ぶんしか見ていないため、台風や寒波のような急変に弱い構造です
